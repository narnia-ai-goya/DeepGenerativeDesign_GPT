모든 수치가 config에서 나옴 — 스크립트에 하드코딩 없음
처리 — 6단계 (text-first 전체 경로)
  1. render cond_render_pv.py 도메인 기하를 6방향 1024px 렌더 → renders/. 도메인당 캐시.
  2. masks cond_render_masks.py 고정/하중 영역의 가림 마스크 → masks/. 스타일이 침범하면 안 되는 곳.
  3. ref text2img_style_ref.py SDXL t2i(descriptor + ref_common) → 중앙 crop 0.35 → 1024 확대 → 256개 문턱값 전수 탐색으로 검정 35% 이진화. 결과는 “검정 구조 / 흰 구멍” 두 색 타일.
  4. inpaint cond_stylize_inpaint_refip_xattn.py SDXL inpaint + IP-Adapter(ref) + cross-view attention. renders에 마스크 밖 영역만 스타일을 새김 → remask/.
  5. normalize nonblack_to_white.py 휘도 정규화. BC 영역은 검정(=재료)으로 채워 보호 → white/.
  6. img2img cond_img2img_consolidate.py SDXL img2img(ip_scale 0, strength 0.7 → 실제 28 step)로 6뷰 톤 통일 + 구멍 경계 선명화.

생성 — 확산 과정에 물리를 개입

direct3ds2 · GPUfenics 서브프로세스 generate_with_physics_guidance.py
입력 — 4갈래가 합류
conditioning/<style>/v*.png
Stage A 산출 · 형상의 “모양”을 결정
voxel.npz
Stage 0 산출 · 설계 영역 + BC 격자
fea_domain/ + fea_shared.msh
Stage 0 산출 · in-loop FEM이 쓰는 도메인과 tet
stages.mesh (~40개 값)
seed 42, --deterministic, FEA_NORMALIZE=0
처리 — 2단 cascade, 매 step guidance
  1. dense 64³ latent에 직접 gradient guidance: 영역 밖 억제 out_w 30, BC 유지 bc_w 10, 부피·대칭·두께·최소반경, 그리고 FEM compliance fea_w (warmup 0.3 이후, SIMP penal 2) — 도메인별 bracket 1.5e-12 · mm 7.5e-12 · link 4.5e-14.
  2. in-loop FEM fenics_fea_bracket.py 서브프로세스로 호출(FEA_FENICS_BIN). fea_shared.msh에 현재 밀도를 실어 선형탄성을 풀고 compliance의 민감도를 돌려줌. 하중 방향은 LOAD_MODE로 전달.
  3. sparse 512³ 50 step. 표면 법선/Laplacian 정칙화(sp_lap_w 50), 내부 채움 sp_interior_w 10, 최소 반경, FEM 항 sp_fea_w (도메인별 3e-11 / 1.5e-10 / 9e-13).
↳ 두 cascade 모두 같은 하중 방향을 씀. stages.mesh.load_mode ≠ stages.fea.force_dir이면 orchestrator가 실행 전에 중단.

STAGE D

검증 — 사후 FEA

fenics fea_prep_and_run.py
입력
final.obj
배포 형상을 그대로 검증
fixed_remesh.stl · load_remesh.stl
BC면. 원본 CAD peg는 삼각형이 너무 커서 6 mm 근접 판정을 통과 못 함 (link는 peg 면의 약 29%를 놓침) → remesh판을 씀
stages.fea
E 110 GPa, ν 0.3, 1000 N, force_dir, tet_size
처리 — 준비 후 별도 프로세스에서 해석
  1. 표면 정리 pymeshlab + pymeshfix 등방 remesh(target_edge_mm — bracket·mm 2.5 mm, link 1.5 mm) → 정점 병합·비다양체 복구·구멍 닫기 → 최대 성분만 남겨 watertight 보장. quadric decimation은 쓰지 않음 — 얇은 격자 부재가 사라지므로.
  2. tet + 해석 fea_tet_from_mesh.py (서브프로세스) gmsh HXT로 4면체 생성 → DOLFINx 선형탄성. 고정면 클램프, 하중면에 1000 N 분포. 실패 시 escalation(HXT→Delaunay→edge 확대→repair fallback).
↳ pymeshlab과 gmsh/dolfinx는 한 프로세스에 공존할 수 없음 (libstdc++ 심볼 충돌). 프로세스 분리가 이 단계의 전제.
산출
fea_input_clean.stl
해석에 실제로 들어간 표면 — 재현·디버깅용
fea_tet_summary.json
compliance, vm_max, u_max, n_tet_cells, force_dir
재실행
refea.py가 값이 없거나 범위를 벗어난 실행만 골라 직렬로 다시 계산. gmsh 병렬 실행이 불안정하기 때문.

이번 변경 — 검증 입력을 hybrid.obj → final.obj 로

배포하는 형상을 검증하는 것이 맞고, 부수적으로 tet 생성이 훨씬 안정적입니다. 10개 실행 전부 첫 시도에서 통과(기존에는 4건이 escalation, 1건은 8개 경로 전부 실패). compliance는 대체로 2~4% 증가하며, ON/OFF가 같은 단계에 착지하므로 ΔC 비교가 처음으로 동일 기준이 됩니다.

파일 계보 — 누가 만들고 누가 읽는가

특히 같은 기하가 두 가지 판본으로 존재하는 이유가 여기 있습니다. 원본판과 remesh판을 쓰는 곳이 각각 다르고, 그 선택마다 측정된 근거가 있습니다.

산출물만든 단계읽는 단계왜 이 판본인가
original_DesignSpace.stl
원본		 손으로 제작Stage 0(복셀·fea_domain) · Stage A(렌더) 복셀 격자의 pitch·origin이 이 STL의 bbox에서 나옴. remesh는 외곽 모서리를 둥글려 (link 최대 1.47 mm) 생성 좌표계 자체를 옮김. gmsh도 bracket의 remesh 도메인은 “겹치는 facet”으로 거부.
*_remesh.stl Stage 0 · remeshStage C · Stage D · Stage B(in-loop peg면) 원본 CAD peg는 큰 평면 하나가 삼각형 몇 개뿐이어서, 솔버의 6 mm 정점 근접 판정에 경계 노드가 걸리지 않음.
voxel.npz Stage 0 · voxelStage B 64³ 하나로 bc_proper(고정·하중 채널)와 bracket_occ(설계 영역 점유) 두 역할을 겸함.
fea_domain/ Stage 0 · fea_domainStage B의 in-loop FEM 솔버가 고정된 세 파일명을 디렉터리에서 찾음. 역할별로 판본이 다름 — 설계 영역은 원본, peg는 remesh.
fea_shared.msh Stage 0 · fea_meshStage B 전 실행이 공유 tet 대상이 설계 영역이라 프롬프트와 무관하게 동일. 실행마다 만들 필요가 없음.
conditioning/<style>/v*.png Stage A · img2imgStage B image-first는 이 경로에 직접 6뷰를 넣는 것이 전부 — 두 진입점이 만나는 지점.
mesh.objStage BStage C guidance가 만든 원 형상. peg도 설계영역 clip도 아직 없음.
hybrid.objStage C · union+clipStage C · remesh 중간 산출물. 검증에는 더 이상 쓰지 않음.
final.objStage C · remesh+smooth Stage D · 결과 렌더 파이프라인의 배포 형상. 검증 대상이자 그림에 실리는 메시.
fea_tet_summary.jsonStage D 비교 표 · refea.py 건전성 검사 compliance 상한(1 J)을 넘으면 퇴화한 tet로 보고 실패 처리 — 쓰레기 값이 표에 들어가지 않도록.

실행 — orchestrator는 --config와 경로만 넘긴다

명령하는 일
run_prep.py --domain allStage 0 · 도메인당 1회. 출력이 있으면 건너뜀
run_conditioning.py --domain … --style …Stage A · text-first 6단계
run_from_text.pyStage A → B → C → D 전체
run_from_image.py --stage gen,post,feaStage B → C → D (조건 이미지가 이미 있을 때)
run_ablation.py같은 스테이지 함수로 variant별 실행 → abl/<variant>/
refea.py --domain allStage D만 직렬 재실행

모든 하이퍼파라미터는 configs/<dom>.json의 stages.*에 있고, 스크립트는 apply_config()로 그 값을 argparse 기본값에 주입합니다. orchestrator가 넘기는 것은 --config와 실행별 입출력 경로뿐이라, 값을 바꾸려면 config만 고치면 됩니다. 세 도메인은 완전히 같은 코드 경로를 타고, 값만 다릅니다.
